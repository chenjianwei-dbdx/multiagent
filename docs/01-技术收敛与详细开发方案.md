# 办公域多智能体：技术收敛与详细开发方案 v1.1（建议稿）

日期：2026-09-30。输入基线：[Master v1.0](reference/MASTER-v1.0.md)。

本文是原文的实施补充，不表示项目已经实现或通过验收。保留原文技术栈、两个专家、开发顺序及 I1–I10；新增规则均为建议默认值。原文中的开发指令作为需求分析，不代表本次已经启动编码。

## 1. 收敛结论

系统定位：单机、单用户、单执行器的办公文档装配与验证工具。先实现 CLI；以确定性程序作为业务核心，以两个 LLM 专家提供判断，以 LangGraph 提供可恢复流程。

首个交付场景：契约化周报模板＋UTF-8 Markdown/粘贴文本→原文绑定→DOCX→来源与结构格式验证→唯一交付。

不增加 CrewAI、AutoGen、第二套工作流、向量数据库、消息队列、前端框架或通用文档 IR。当前空仓库没有迁移负担。

### 1.1 技术决策表

| 层 | 收敛选择 | 使用边界 |
|---|---|---|
| Python | 3.12，`.python-version` 锁定 | MVP 不同时承诺 3.13；后续独立兼容验证 |
| 工程 | uv、src layout、pyproject.toml、uv.lock | CI 使用 `uv sync --frozen`；提交锁文件 |

| 专家 | PydanticAI | 两个 Agent；结构化输出、受限工具、调用预算；不使用其额外持久工作流能力 |
| 编排 | LangGraph StateGraph | 条件边、interrupt、resume；SQLite checkpointer 单独数据库 |
| 数据库 | Python sqlite3＋版本化 SQL migrations | 不引入 ORM/Alembic；短事务＋显式 repository |
| 文件池 | pathlib、hashlib、tempfile、os | 文件不可变；临时写入、校验、同文件系统原子提升 |
| DOCX | docxtpl、python-docx、Jinja2、lxml | docxtpl 替换受控占位符；python-docx 读取和测试造样；lxml 检查 OOXML |
| CLI | Typer | 只调用 Application Service；标准输出支持 JSON |
| 配置 | pydantic-settings＋标准库 tomllib | 建议以 app.toml/models.toml 替代原文 YAML，减少一个依赖；密钥只来自环境/本地秘密配置 |
| 测试 | pytest、Hypothesis、Ruff、mypy | 安全不变量、真实文件集成、故障注入、属性测试 |
| 锁 | filelock 或等效跨进程文件锁 | 一个 OMAS_HOME 同时只允许一个写执行器；不是多 worker 调度 |
| Web（后置） | FastAPI＋Uvicorn | MVP 验收后加入 optional extra；仍调用同一 Service |

版本策略：这里不编造已验证的版本组合。阶段 0 选择官方稳定版本、安装解析依赖、完成兼容性冒烟后提交精确 uv.lock，记录版本和验证命令到 dependency-baseline.md。运行时 Python 3.12、Pydantic 2 是明确约束；其他直接依赖采用经实测的兼容范围＋精确锁文件。不要把官网最新示例与旧锁文件混用。

### 1.2 开发前必须通过的兼容性探针

1. PydanticAI 受控测试模型→一个工具调用→Pydantic 输出→验证重试上限→usage 获取，全程禁止网络。
2. LangGraph＋SQLite saver：进程 A interrupt；进程 B 使用同一 thread_id resume；记录节点重执行次数。
3. docxtpl：中文、`<>&`、连续空格、Tab、LF、emoji；渲染后以独立 XML extractor 对比文本及样式。
4. 验证 python-docx/lxml 对所选锚点、段落、表格单元格和编号结构的读取。

探针用于确定版本与模板子集；不提前建设完整 Graph。

## 2. 原文中必须补齐的契约

| 未闭合点 | 建议实施规则 |
|---|---|
| Planner 可否创造模板没有的槽位 | 不可。只能在 TemplateContract 的 section/slot 集合内规划语义和顺序；模板定义的必需槽不能删改 |
| Markdown 是否转富文本 | MVP 按原文装配，Markdown 标记保持原样；不做 Markdown→Word 转换，不静默删除 `#`、`**` 等字符 |
| Slot 枚举含 chart/image，但输入只有文本 | v1.1 MVP profile 只启用 text_block 和固定表格单元格文本绑定；图像、图表、动态表格显式拒绝，不生成空壳实现 |
| required 槽允许放弃 | 用独立 SlotOverride 记录；不把 missing 改成 bound。仅允许模板声明 `allow_user_omit=true` 的槽位由用户显式留空 |
| missing 仍强制 producer | 建议以判别联合表达 BoundBinding/MissingBinding/InvalidBinding；只有 bound 必填 producer。无来源时不伪造 user/upstream/viz |
| Gate A 在流程图中不明显 | 固定增加 render 前的 provenance_precheck；现有 provenance_gate 作为 Gate B |
| provenance 只核验必需槽 | 扩展到全部动态槽、静态文本和所有允许承载文字的 OOXML part，避免槽外注入漏检 |
| Format unknown 怎么处理 | required check 出现 unknown 即禁止 finalize；不能仅以没有 blocker 判断通过 |
| Gate pass 能否重用 | 只对同一 candidate sha、模板版本、IR sha、规则版本有效；candidate 变化则重跑 |
| Agent 路径权限怎么实现 | Agent 只有受限材料工具，没有 shell/文件写工具；工具宿主有 task scope。Python 对象封装不是恶意宿主代码的操作系统沙箱 |
| local_only 只限制正文是否足够 | 文件名、片段、用户意图、模板、错误信息、追踪和自动遥测同样受策略约束 |
| checkpoint 落后业务提交 | 以 Ledger 已 committed 输出复用；不盲目重复副作用；无法验证的 checkpoint 不能继续交付 |

上述 profile 是明确的范围收敛建议，并非宣称原文已排除全部表格。如果第一期必须支持动态行表格，应先扩展 cell provenance 契约和测试，再估算工期。

## 3. 模板子集：把“契约化”变成可执行规范

### 3.1 模板包

每个版本目录包括 template.docx、contract.json、styles.json、static-map.json、manifest.json。版本记录同时绑定全部文件 hash 和 extractor_version；同 DOCX 重新提取也生成新版本。

提取由“程序读取结构＋人工维护语义 sidecar”完成。程序不能从字体、槽位名字可靠推断 required、语义要求和业务允许豁免条件。

sidecar 示例：

```json
{
  "schema_version": "1.1",
  "template_id": "weekly-report",
  "slots": [
    {
      "slot_id": "sales_summary",
      "placeholder": "{{ sales_summary }}",
      "kind": "text_block",
      "required": true,
      "allow_user_omit": false,
      "semantic_requirement": "本周销售情况",
      "style_key": "body"
    }
  ]
}
```

### 3.2 MVP 支持与拒绝

- 动态占位符位于正文普通段落或固定表格单元格内；占位符独占一个段落，完整位于一个 run，每槽恰好出现一次。
- 一个槽可绑定多个 span；各 span 输出独立段落，顺序明确。段落边界是结构，不补连接词。span 内 LF 映射为换行，Tab 映射为 Tab；禁止悄悄 trim/collapse 空白。
- 保留固定标题和普通静态页眉页脚；静态表格允许，但不支持动态增删行、复杂合并表和嵌套表的动态槽。
- 第一版拒绝 `{{r ...}}`、subdoc、自定义 filter、表达式、循环、include、宏、任意 Jinja 控制语法；只允许白名单变量节点。StrictUndefined＋autoescape=True。
- 第一版拒绝动态页眉页脚、域代码（含自动页码）、修订、批注、文本框、脚注/尾注、OLE、嵌入包、宏、外部关系和无法枚举文字载体的结构。书签可由受信程序用作锚点。
- 禁止不合法 XML 字符及会触发 docxtpl 特殊控制行为的用户控制字符（例如 `\a`、`\f`）。报错要求用户修正，不能过滤后继续。
- split-run 占位符先拒绝并给出定位；不以“任意 Word 模板可用”为验收目标。

注册时即检查 unsupported findings；发现不支持的结构不激活模板。模板提取不调用 LLM。

### 3.3 定位与格式

提取时为槽位生成稳定锚点（例如受控 bookmark），记录 part、锚点 ID、槽位顺序、段落/单元格结构签名；在兼容性探针中证明锚点跨渲染仍存在。不要仅保存绝对 paragraph index，因为插入多个段落会改变后续索引。

字体检查解析 direct formatting→character/paragraph style→basedOn→docDefaults，检查 eastAsia 与 latin；遇到无法解析的 theme 或继承返回 unknown。字号统一半磅、边距/缩进统一 twip，StyleSpec 写明容差。编号核对 numbering.xml 引用及级别，不仅检查 numPr 存在。

这些检查证明 OOXML 属性满足契约，不证明分页、实际字体可用或 Word/其他办公软件像素一致。MVP 不承诺页面级视觉一致性。

## 4. 数据契约与权威写者

### 4.1 核心对象

所有 ID 由程序生成；hash 为 SHA-256 十六进制；时间用 UTC。canonical text 以 UTF-8 存文件，span `[start,end)` 按 Python Unicode code point 计数，不是字节或 UTF-16 单元。禁止空 span，范围必须满足 `0 <= start < end <= len(text)`。canonical_hash 对完整 UTF-8 文件，span_hash 对 slice 的 UTF-8 编码。

| 对象 | 必要字段 / 规则 | 权威写者 |
|---|---|---|
| Task | id、status、template_version_id、data_policy、epoch、active refs、request_id | TaskService/TaskRepository |
| Artifact | id、task_id、kind、relative_path、sha、size、created_by_run、source lineage | ArtifactStore 提交服务 |
| ContentPlanIR | schema_version、template_version_id、sections、slots | Planner 输出经 PlanValidator 验证后由 PlanService 提交 |
| BindingIR | schema_version、plan ref、material_set_digest、slot bindings | BindingService；Assembler 只提交提议 |
| SourceSpanRef | artifact_id、canonical_sha、start、end、span_sha | resolve_span 生成，提交和渲染时再次验证 |
| SlotOverride | slot_id、decision_id、epoch、action=omit、理由 artifact ref | 用户决策服务 |
| DocxRenderIR | template refs、受控 anchors、source refs、style keys、override refs | RenderIRBuilder |
| GateReport | candidate_sha、IR_sha、template_version、rule_version、check results | GateRunner |
| Delivery | candidate ref、final sha、manifest ref、operation_id | Finalizer |

Binding 判别联合：bound 必须有非空 source_refs、producer 合法且与原料来源一致；missing 必须无 refs；invalid 带错误码。producer 由材料注册信息验证，不让 LLM 任意声明 viz。数据类型保留扩展能力，但 MVP profile 拒绝 viz。

Agent 输出中所有多余字段（如 text、summary）一律拒绝。Pydantic frozen 不是深不可变保证：不可变性最终依赖文件只追加、读取 hash 验证和受控写接口。

### 4.2 Agent 输出再收敛

建议工具 resolve_span 返回程序登记的 `span_handle` 及 SourceSpanRef。Assembler 输出 DTO 使用 `slot_id + span_handles + status`；BindingService 将 handle 转为正式 BindingIR。handle 绑定 task/run/material version，不能引用其他任务或未通过工具解析的材料。

这是对“Assembler 输出 BindingIR”的边界实现细化：专家表达绑定意图，程序拥有持久化 BindingIR 的写权，且 hash 不来自 LLM 自报。也可让专家回传完整 SourceSpanRef，但必须核对工具签发记录与实际文件；不要把“模型输出过一个 hash”当证据。

### 4.3 SQLite

保留原文九张业务表，增加 schema_migrations、user_decisions、slot_overrides、gate_reports（只存摘要/ref）。如使用 span_handle，再增加 resolved_spans 或等价受控索引。

关键约束：

- tasks.request_id UNIQUE；user_decisions.decision_id UNIQUE；同一 key 不同 request digest→IDEMPOTENCY_CONFLICT。
- operations.operation_key UNIQUE；只允许 intent/committed/abandoned；业务输出引用与 committed 状态在同一事务更新。
- node_runs 的尝试单独记录；bindings 按 task+epoch+binding version+slot 唯一，保留历史。
- deliveries.task_id UNIQUE（MVP 每 task 仅一次最终交付）；deliveries.operation_id UNIQUE。
- events 使用递增序号；存 error code、引用、计数，不存正文/工具完整结果/异常完整响应。
- 每连接显式 `foreign_keys=ON`、busy_timeout；建议 WAL、synchronous=FULL；不在数据库事务中等待 LLM 或渲染。
- 迁移逐版执行、事务化并记录 checksum；不要启动时 silently recreate tables。

LLM 原始输出、工具参数/结果、完整 plan/binding/gate report 放文件；SQLite 只保存 refs 和有限元数据。cost 不可得时记 null，不能假装为 0。

## 5. Application Service 与文件能力边界

建议接口（语义定义，非已实现 API）：

```python
submit(command: SubmitTask) -> TaskReceipt
status(task_id: TaskId) -> TaskView
respond(command: RespondTask) -> DecisionReceipt
cancel(command: CancelTask) -> TaskView
recover(task_id: TaskId) -> TaskView
events(task_id: TaskId, after: int) -> EventPage
export(command: ExportTask) -> ExportReceipt
```

SubmitTask 固定 template_version、材料输入、意图 artifact、data_policy、request_id；RespondTask 包含 decision_id、expected_epoch、awaiting_event_id、action 和附件 refs。cancel/export/template extract 等会写文件或状态的外部操作也要求幂等 key；status/events 不需要。

节点只获得 NodeArtifactWriter(run_id)，不能接收任意绝对路径；Finalizer 单独获得 DeliveryWriter。模型工具依赖对象不能持有可写 Ledger/Finalizer/shell。所有 read/search/resolve 操作在宿主强制 task scope，不能相信工具参数中的 task_id。

ArtifactStore 用服务器生成的路径，校验根目录和所有祖先 symlink；安全打开需防止校验与使用之间的链接替换。MVP 假设 OMAS_HOME 由当前用户独占，不声称抵御同 UID 恶意本地进程；若要运行不可信 Python 插件，必须另行设计进程/OS 沙箱。

## 6. 原料工具与 LLM 行为

材料索引由确定性程序提取文件元数据、Markdown 标题及范围、段落边界；不生成模型摘要。搜索 MVP 采用 canonical 文件内字面/关键词搜索及可解释评分，全文不进入 SQLite FTS；无向量数据库。

建议预算默认值：一次 list 50 项、search top_k≤10、snippet≤200 字符、单次 read≤8,000 字符、每轮工具≤20 次、总读取≤40,000 字符、schema repair≤2 次、调用超时 120 秒。全部可配置，预算不足→明确错误或 awaiting_user，不能猜测补全。

Planner 读取用户意图与模板语义，不读原料正文；验证输出槽位集合、required、kind、style 不越权。Assembler 读取模板需求、索引和原文工具结果，按业务语义选择；只能绑定精确来源，不润色。LLM 选择的内容是否语义合适仍可能出错，来源校验不等于语义正确性；用独立人工标注样例评估槽位选择，MVP 不引入 Reviewer 替代验收。

模型策略：先使用一个支持中文、工具调用和结构化输出的本地模型承担两种角色，不按角色先拆大模型/小模型。模型 ID 由本地实际安装与探针决定；开发默认 FakeModel，真实本地模型 smoke 是最终验收项。云模型仅为显式 llm_allowed 的可选配置，不设隐式 fallback。

DataPolicyGuard 在 provider/client 初始化和每次请求之前执行；默认关闭云 tracing/telemetry。local_only 的本地端点必须在管理员配置的 loopback allowlist 内，不接受用户输入任意 base_url、代理或重定向；本地模型本身不具备云转发。拒绝时在任何网络字节发出前停止，并记录元数据错误。缺少合规模型→awaiting_user，保持策略不变。

llm_allowed 应由用户看到具体 provider 和 endpoint 后显式选择；改变策略必须记录用户 decision，不能由补料或模型错误自动触发。输入材料中的“忽略规则”等文字始终作为数据。

## 7. 渲染与两道来源门禁

实际链路：

```text
ingest → bind_template → inventory → plan → assemble_bind → gap_check
  → build_render_ir → provenance_precheck(A) → render_docx
  → provenance_gate(B) → format_gate → finalize
```

Gate A 验证全部来源、task scope、文件 hash、模板 hash、source spans、模板静态引用、override 和 active epoch。DocxRenderIR 不包含自由正文；静态内容也不能由调用者传 string，而是 TemplateStaticRef 指向版本化模板。

Renderer 对外只接受 RenderIRArtifactId；内部调用 ArtifactStore 解析受验证 source refs。docxtpl 内部 context 出现字符串是必要实现，不应把这种内部字符串误判为自由文本入口；关键在于调用者不能传任意 context/text 或伪造 template_static。

Gate B 使用独立 OOXML extractor：

1. 定位所有槽位锚点，验证输出顺序、段落数、单元格位置和重复/缺失。
2. 把 `w:t`、Tab、换行映射为事先定义的文本 token；不能只搜索整个 DOCX 是否包含某段文字。
3. 对动态槽逐 span 精确对比，结构段落分隔单独比对；不做 trim、空白折叠或相似度匹配。
4. 对所有静态文本区域逐项比较模板 static map；没有合法来源的新增文本为 BLOCKER。
5. 枚举文本载体，未支持 part 或 hidden/revision 等结构被加入后直接失败。标记占位符残留，检查数量与区域覆盖。

每个 Gate 输出 pass/fail/unknown、rule_id、severity、locator、expected/actual 摘要和 evidence_ref。正文证据在文件中。总体 pass 必须满足所有 required checks 为 pass；optional unknown 只能作为显式非阻断 finding，不能显示为 pass。

格式验证支持静态段落和动态插入内容；模板有意设置的差异由 StyleSpec 逐区域定义。若格式不确定，candidate 留在 node/out 调试，不进入 deliverables。

## 8. 状态、人工决策与恢复

沿用原文状态枚举。正常流 created→running→completed；缺材料/模型配置→awaiting_user；用户决策后 running；不可恢复失败→failed；显式取消→cancelled。parked 仅保留给显式暂存，不用于替代 awaiting_user。completed/failed/cancelled 在 MVP 为终态；失败后修正可新建 task，进程崩溃导致未完成的 running 可 recover。

单次缺料形成一个 AwaitingEvent（refs/slot IDs，不含正文）；一个事件只接受一次有效决策，携带 expected_epoch 防止旧决策覆盖新一轮。补料保留旧文件，递增 epoch，复用模板和有效 plan，重新 inventory/assemble_bind/gates；不改变 task_id。

omit 仅对合同允许的槽位生效：保留 missing，新增 override；渲染空段落且不插入“暂无”等文字；manifest 披露。不可豁免槽位拒绝 omit。用户如需要“暂无”，把该文字作为明确用户材料入池后绑定。

LangGraph 使用 task_id 作为稳定 thread_id；resume 只传 decision ref。interrupt 节点会从头执行，不能依赖内存跳过副作用。[官方 interrupt 说明](https://docs.langchain.com/oss/python/langgraph/interrupts)

将等待事件准备与 interrupt 分开：gap_check 幂等提交 AwaitingEvent；wait_for_input 只根据该持久事件调用一次固定位置 interrupt，恢复后验证决策并交给程序 apply。不能在恢复时因为 Ledger 已有决策而绕开 interrupt，导致 resume 消息失配。外围按 checkpoint 状态判断应 resume 还是重放待执行节点，不捕获 GraphInterrupt 当普通异常。

### 8.1 节点幂等协议

operation_key=task_id+epoch+node_name+input_digest+implementation_version。LLM 输入 digest 包含模板、材料集合、模型配置、prompt/tool schema 版本。运行前查 committed；已存在则 hash 验证并直接返回 output refs。

未提交：短事务登记 intent→创建 node_run→在 run/work 写文件→校验并提升到 out→同一 Ledger 事务登记 artifacts、更新业务引用、operation committed、run done→Graph 接收轻量 refs。失败重试创建新 run，保留历史。

崩溃可能重复调用模型并多花一次费用；只保证业务提交幂等，不承诺外部 LLM exactly-once。

### 8.2 Finalize 与崩溃矩阵

Finalize 输入固定 candidate、IR、gates 和全部 hash；在全局写锁内重新校验其属于当前 epoch、任务未取消且 gates 对应相同 candidate。

| 崩溃点 | 恢复行为 |
|---|---|
| intent 前 | 正常重试 |
| intent 后/临时文件写到一半 | 校验、清理本 operation 临时文件并重试 |
| 文件提升到 out 后、Ledger 前 | 验证 manifest 并重新登记，或隔离无效孤儿；不直接相信文件名 |
| Ledger committed 后、checkpoint 前 | 从 Ledger 复用输出，修复流程进度 |
| deliverables 原子提升后、delivery 事务前 | 对照 intent 和 hash 认领已有文件并补齐唯一 delivery；不生成第二份 |
| delivery committed 后、返回用户前 | 返回已有 receipt，校验交付文件 hash |
| 已登记文件内容变更 | 标记相关 run corrupt、任务失败/阻断 export；保留审计记录，不覆盖修复 |

finalize 临时文件与目标同一文件系统，flush/fsync 后原子提升，平台支持时同步目录；与数据库不能形成跨资源事务。原子提升到记录提交的短窗口可能存在文件，但此时 gates 已通过，服务 export 仍只暴露 committed delivery。

manifest 至少包括 task/epoch、模板所有 hashes、输入 lineage、plan/binding/render refs、gate reports、run/operation、模型调用元数据 refs、DOCX hash、override refs、软件版本/lock digest。deliverable 的唯一可信入口是 Ledger delivery record。

cancel 以边界检查生效：当前不可中止调用可以结束，但取消成功后不得提交新业务输出/交付；需要在最终事务重新检查状态。并发测试验证 cancel 与 finalize 的序列化结果。

## 9. 文件输入校验与运行默认值

建议可配置上限：单文本 5 MiB、单 DOCX 20 MiB、zip 展开总量 100 MiB、entries 2,000、XML 深度 128、单任务材料 50 份。按流读取限制实际解压字节，不能只信 ZIP header；具体数值为初始工程限制，不是已测容量。

文本限定 UTF-8，非法编码拒绝；NFC 与换行是唯一 canonical 改动。保留 raw artifact 以追溯。DOCX 验证 ZIP content types、条目路径/重复名称/大小/压缩异常、宏、外部关系、危险 URI、symlink。lxml 关闭实体解析、网络、DTD，禁用 huge_tree；拒绝 DOCTYPE。

## 10. 阶段开发计划

估算前提：1 名熟悉 Python 的工程师＋编码助手、约定模板子集、已有可用本地模型；人日为粗估，不是承诺。总计约 21–32 人日；复杂模板和模型适配另计。

| 阶段 | 交付内容 | 退出条件 | 估算 |
|---|---|---|---|
| P0 工程与契约 | 依赖探针、DTO、状态机、migrations、Store、Ledger、测试基架 | 离线契约、不可变文件、幂等唯一约束测试通过 | 3–4 |
| P1 确定性闭环 | 模板 extractor/sidecar、IR builder、Renderer、Gate A/B、Format、Finalizer | 无 LLM fixture 生成可追溯 DOCX；注入自由文本和槽外文字被阻断 | 6–9 |
| P2 Assembler | 四工具、scope、proposal 转 Binding、策略、预算、审计 | FakeModel 对抗测试＋真实本地模型能绑定材料 | 3–4 |
| P3 Planner | 语义计划、受模板约束验证、连接 Assembler | 不新增/删除必需槽；多案例正确规划 | 1–2 |
| P4 编排恢复 | Graph、waiting event、respond、resume、reconcile、fault injection | 跨进程恢复、并发重复请求、取消与 finalize 竞态通过 | 4–6 |

仓库采用 Master 目录，增补 services/operation_service.py、services/decision_service.py、services/finalizer.py、security/capabilities.py、security/model_gateway.py、gates/docx_text_extractor.py、graph/nodes/wait_for_input.py、tests/faults/、tests/benchmarks/。不为后置功能创建空实现。

## 11. 验收矩阵

原 T01–T12 保留原编号和含义；新增如下，不替换基线：

- T13 模板静态区域被额外插字、slot 外插字均阻断。
- T14 任一 required gate unknown 阻断，candidate 有但 delivery 无。
- T15 required omit 只在模板许可＋有效用户 decision 下成立。
- T16 旧 epoch/错误等待事件的 decision 拒绝；同 key 不同 payload 冲突。
- T17 中文 NFC、组合字符、emoji、CRLF、Tab、空格的 span/渲染一致性。
- T18 跨任务 ref、伪造 handle、错误 template_static 引用拒绝。
- T19 任意 Jinja 表达式、split-run、不支持的 DOCX part 预检拒绝。
- T20 GateReport 与 candidate/IR/template hash 不一致拒绝 finalize。
- T21 全部崩溃矩阵点跨进程重启，最多一条 delivery。
- T22 local_only 的 system prompt、snippet、日志和遥测均不外发；网关请求计数为零。
- T23 cancel 与 finalize 竞态满足序列化；cancel 成功后不交付。
- T24 CLI 真实本地模型缺料→补料→同 task 完成，模型原始响应与绑定均可追溯。

P0 不变量用确定性测试要求 100%；不能用 FakeModel 通过替代真实 Agent 可用性，也不能用随机 LLM 输出评估数据层幂等。

Format benchmark：至少 20 clean＋20 injected，覆盖字体、字号、对齐、编号、边距、缩进、样式漂移、placeholder 八类；每类至少两个注入案例，保留人工 gold labels。统计 check-level precision/recall/FPR，unknown 独立计数，正例 unknown 计入未检出。建议 MVP 门槛：约定支持子集中的 40 个案例全部按 gold 分类，required unknown 为 0；同时报告各类指标及样本量，不把小样本当通用准确率。

测试命令（实施后应真实存在）：`uv run ruff check .`、`uv run mypy src/omas`、`uv run pytest tests/unit tests/integration tests/invariants tests/faults`、`uv run pytest tests/benchmarks`。测试报告记录实际退出码、版本、平台；没有运行必须写未运行及原因。

## 12. 仍需业务确认但不阻塞 P0/P1 fixture 的事项

1. 是否接受严格模板子集和 Markdown 按原文显示；若不接受，明确需支持的 Word 结构及允许的文本变换。
2. required 槽哪些可由用户豁免；默认全部不可豁免，模板逐槽开启。
3. 真实模型运行环境、模型 ID、机器内存；未配置前可完成离线测试，最终真实模型验收不能宣称完成。
4. 是否需要表格动态行、分页视觉保证；当前建议后置。

无需为这些问题重新选多智能体框架。不要擅自启用云模型，也不要把业务待确认项包装成已批准要求。
